Independent source-level comparison

Sphinx vs. Tailscale Setec

A capability, architecture, and security review focused on whether Sphinx is missing important behavior, whether its sensitive paths are implemented defensibly, and where it stands against Tailscale’s Setec.

1. Executive verdict

Bottom line: Sphinx is not a deficient clone of Setec; it is a narrower, Git-backed, recovery-oriented product with a different trust model. For a single-user Mac guardian and human-operated encrypted repository, Sphinx has several excellent properties and is arguably the better fit. For production workloads that need rotation, live updates, action-scoped administration, backups, SDK integration, or multi-platform key management, Setec is substantially ahead.

Where Sphinx wins

  • Offline passphrase recovery per Relic
  • Portable Git-native ciphertext and history
  • Declarative typed schemas and facet-level revelation
  • No network mutation API
  • Strong path, symlink, size, timeout, and no-cache defenses
  • Authorization policy separated from the Tomb

Where Sphinx trails

  • No first-class versions, activation, rollback, or deletion
  • No workload SDK, polling store, watcher, updater, or keyring
  • No online write/admin API
  • No periodic refresh or backup subsystem
  • macOS-only guardian key custody
  • Less mature testing and observability

Most important security work: add immutable/signed Tomb revision verification, correct and test tagged-node identity semantics, harden Keychain access controls, prevent accidental non-loopback plaintext serving, add API browser defenses and request concurrency limits, and improve audit outcome/durability semantics.

2. Scope and method

The review inspected all security-relevant Sphinx packages and commands, all Setec server/database/ACL/audit/TPM paths, Setec’s client store and operational documentation, and both test suites. The comparison is pinned to the revisions above rather than to moving branches.

  • Sphinx: 34 tracked files, approximately 3,251 Go/source lines in core directories, 12 top-level tests.
  • Setec: 47 tracked files, approximately 7,325 Go/source lines in core directories, 36 top-level tests.
  • go test ./... and go vet ./... passed for Sphinx under its Nix development environment.
  • Setec’s packages except tpmkey passed; the TPM test build could not find openssl/aes.h in this Darwin environment. This is an environment prerequisite failure, not evidence of a Setec defect.
  • govulncheck was unavailable, so this report does not claim a dependency-CVE assessment.
Limitation: This is static source review plus unit/build validation. It did not test a live tailnet, macOS Keychain ACL prompts, Tailscale Serve configuration, AWS KMS, a physical TPM, Git hosting controls, or adversarial runtime load.

6. Indexed Sphinx security and robustness findings

  1. S-01 — Tomb provenance is not authenticated
  2. S-02 — Tagged-node identity semantics are unclear/likely broken
  3. S-03 — Keychain item lacks explicit hardened access policy
  4. S-04 — Plain HTTP and browser-access footguns
  5. S-05 — No rate or concurrency controls
  6. S-06 — Audit records judgment, not disclosure outcome
  7. S-07 — Path checks remain TOCTOU-prone
  8. S-08 — Static Decree and unchecked permissions
  9. S-09 — Security-critical test gaps

High S-01 — Tomb content integrity is checked, but author provenance is not

MAC verification detects accidental or unauthorized modification of an existing encrypted document by someone who cannot construct a replacement. It does not prove who authored a replacement: the guardian public key is available, so any Tomb writer can generate a fresh data key, encrypt chosen Essence, compute a valid MAC, and wrap the key to the Guardian. Sphinx explicitly assumes Tomb writers are trusted and permits mutable branch/tag references.

Impact: compromise of Git write credentials, branch protection, or an authorized writer can silently replace production credentials with attacker-selected values. This is the most important difference from “ciphertext integrity” and should be explicit in deployment guidance.

Recommendation: support immutable commit allowlists immediately; then verify signed commits/tags against configured signer identities. Record the verified commit and signer in every Chronicle entry. Refuse mutable refs in a hardened mode. Consider a manifest signed separately from the repository.

Evidence: docs/PRD.md:96–106, 223; internal/tomb/tomb.go:108–121; internal/secret/encryption.go:80–130.

Medium S-02 — Tagged-node handling does not match Setec’s defensive identity model

Sphinx requires both UserProfile and Node to be non-nil, then carries both login and tags into a principal; Decree identity matching is OR across login and tags. Setec instead checks Node.IsTagged() and treats a tagged device as tag-only, otherwise as a user. Depending on LocalAPI response shape, Sphinx may reject tagged nodes entirely or may accidentally preserve a human login semantic for a tagged device.

Recommendation: mirror Tailscale semantics explicitly: tagged node → tags only; untagged node → verified user login only. Add fixture tests for tagged device, user device, missing profile, missing node, empty login, and mixed fields.

Evidence: internal/identity/tailscale.go:24–35; internal/policy/policy.go:73–87; Setec server/server.go:295–325.

Medium S-03 — Keychain storage does not set an explicit accessibility or code-bound access policy

The generic-password item is added with service, account, and value only. No kSecAttrAccessible or SecAccessControl policy is selected. The effective behavior therefore depends on platform defaults and the login Keychain state. The PRD already lists signed/notarized binary-bound controls as future work.

Recommendation: choose and document an explicit accessibility class (at minimum when-unlocked), use SecAccessControl where unattended LaunchAgent requirements permit, bind access to the signed/notarized binary or a dedicated access group, and test upgrade behavior. Keep the current non-overwrite initialization check.

Evidence: internal/keychain/keychain_darwin.go:24–106; docs/PRD.md:92, 224.

Medium S-04 — The daemon can be exposed as plaintext HTTP and the secret endpoint is browser-callable

The secure documented deployment binds loopback and places Tailscale Serve HTTPS in front. The command nevertheless permits any listen address and always calls ListenAndServe, with no guard against 0.0.0.0 or a tailnet address. The reveal endpoint is a normal GET and has no Setec-style forbidden Sec-* header requirement. Same-origin policy usually prevents a hostile page from reading a cross-origin response, but browser navigation/extensions and future CORS changes enlarge the risk.

Recommendation: reject non-loopback binds unless an explicitly named unsafe flag is supplied; optionally embed tsnet/TLS; make reveal POST with JSON or require a forbidden browser header; enforce HTTPS in the client except for loopback; add Referrer-Policy: no-referrer and retain Cache-Control: no-store.

Evidence: cmd/sphinx/protect.go:50, 113–121; internal/server/server.go:65–69, 221–228; Setec server/server.go:337–362.

Medium S-05 — Size/time limits are good, but there is no admission or concurrency control

Sphinx caps encrypted Relics at 1 MiB and configures HTTP timeouts, which is better than Setec’s current API. However, every authorized request can perform filesystem resolution, decryption, YAML parsing, schema walking/loading, and response encoding concurrently. There is no global/per-principal semaphore, rate limit, or response-size accounting.

Recommendation: add a bounded decrypt semaphore, per-principal rate limiting, schema caching keyed by immutable revision, and metrics for requests, denials, decrypt failures, latency, and in-flight work. Return 429/503 under admission pressure.

Evidence: internal/server/server.go:21, 111–162, 190–211; cmd/sphinx/protect.go:113–115.

Low–Medium S-06 — Chronicle entries describe authorization judgment, not actual disclosure outcome

An allowed event is written before path resolution, file read, decryption, schema validation, facet selection, and response serialization. Thus an “allowed” entry can mean anything from “authorized but missing” to “secret returned.” Denied-event audit failures are logged but do not alter the response; allowed events fail closed on audit failure. The logger serializes writes with a mutex and forces mode 0600, but does not Sync entries.

Recommendation: record a final outcome (denied, not_found, integrity_failed, revealed, client_disconnected where knowable), status code, and revision. Sync according to a documented durability policy, and add a tamper-evident/remote sink interface.

Evidence: internal/server/server.go:98–162; internal/audit/audit.go:23–47; docs/PRD.md:160–174, 227.

Low S-07 — Symlink validation is careful but path-based and therefore raceable

EvalSymlinks/Lstat checks are strong against static traversal. A concurrently writable local Tomb can swap a directory or target between validation and open/rename. Authoring’s check-then-create also allows races, and directory sync is omitted after atomic rename. This is low risk under the documented trusted-host/trusted-writer assumptions, and remote Tombs are detached snapshots.

Recommendation: use descriptor-relative operations (openat/O_NOFOLLOW equivalents where available), refuse symlinks on the final component, fsync the containing directory after rename, and document local Tomb ownership requirements.

Evidence: internal/server/server.go:164–177; internal/relic/relic.go:104–178; internal/tomb/config.go:25–94.

Low–Medium S-08 — Decree freshness and filesystem permissions are operational weak points

The Decree is loaded once at startup and its ownership/mode are not checked. A mistakenly group/world-writable Decree can become an authorization escalation path. Policy changes and remote Tomb changes require daemon restart.

Recommendation: reject insecure Decree ownership/modes by default, support atomic watched reload with parse-before-swap, record a policy digest/version in Chronicle entries, and fail safely if reload validation fails.

Evidence: cmd/sphinx/protect.go:99–102; internal/policy/policy.go:34–61; docs/PRD.md:106.

Medium S-09 — Tests do not yet match the security claims

The existing tests cover policy, schema, encryption, Tomb, configuration, and basic server behavior, but there are no direct tests for audit durability/failure behavior, Tailscale identity mapping, Keychain access behavior, command lifecycle races, HTTP security headers, maximum document handling, browser defense, Git credential/environment handling, or concurrent requests. Setec has roughly 3× the top-level tests and reusable integration helpers.

Recommendation: prioritize adversarial tests around identity shapes, symlink swaps, malformed/oversized YAML, audit sink failures, concurrent decrypts, mutable refs, Keychain errors, and full end-to-end reveal. Add fuzzers for path, policy glob, schema, encrypted Relic parsing, and Tomb URL/ref parsing.

Evidence: Sphinx test inventory; internal/server/server_test.go (32 lines); Setec setectest/ and broader package tests.

8. Security choices Sphinx should preserve

Fail-closed request path

Identity, path validation, policy, audit availability for allowed requests, public-key binding, MAC, schema validation, and facet existence all gate disclosure.

Narrow network surface

Only health and read-only reveal are exposed. Tomb mutation stays offline/local, avoiding Setec’s remote administrative endpoints.

Strong file/path hygiene

Strict segments, root containment, symlink checks, private cache/directories, mode-0600 files, temporary files, atomic rename, and document size limits are all sound defaults.

Key invariants

Exactly one guardian public key is required and bound to the Tomb; one explicit passphrase recovery envelope is required.

Least disclosure

The server returns only validated Essence, optionally one field, rather than the full encrypted document or public metadata.

Recovery design

Passphrases are read from /dev/tty with echo disabled, never accepted by argument/environment, and can recover without the online identity.

Policy separation

Keeping the Decree outside the Tomb prevents a normal Tomb writer from directly granting network access.

Safer HTTP defaults

Sphinx sets no-store, nosniff, restrictive CSP, response/document limits, server timeouts, and graceful shutdown—several areas where Setec can improve.

Capabilities not worth copying blindly

  • Remote mutation: only add it if Sphinx intends to become a multi-operator service. It materially expands authorization, CSRF, validation, and audit surface.
  • Plaintext persistent client cache: useful for availability, but contrary to Sphinx’s current exposure-minimizing posture. Make it opt-in and loudly documented if added.
  • Dashboard/debug endpoints: observability is useful, but avoid exposing metadata unless it is separately authorized and hardened.
  • Whole-database storage: it simplifies transactions but sacrifices Git-native portability and creates write-amplification/blast-radius tradeoffs.

10. Decision guide

Choose/continue Sphinx when…

  • The Temple is a trusted Mac and operators are humans.
  • Git review/history and offline recovery matter.
  • Secrets are structured and facet-level release is valuable.
  • Read-only network access is a feature, not a limitation.
  • Restart-based refresh is currently acceptable.

Choose Setec when…

  • Production applications consume and rotate secrets continuously.
  • You need versions, staged activation, rollback, deletion, polling, or keyrings.
  • Tailnet-managed action permissions are preferred.
  • AWS KMS/TPM, encrypted S3 backup, metrics, and SDKs are required.
  • Linux/service deployment matters more than portable passphrase recovery.
Practical conclusion: Do not rewrite Sphinx into Setec. Keep its differentiated schema + Git + recovery architecture, but borrow Setec’s identity semantics, anti-browser API posture, action/version vocabulary, client update model, integration test strategy, observability, and hardware/cloud key abstractions.
